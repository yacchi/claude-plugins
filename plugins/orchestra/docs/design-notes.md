# Design notes

Why orchestra is shaped the way it is, and the observations that drove each change. The mechanism itself is specified in `skills/run/SKILL.md` and `skills/run/references/` (loaded by the model); this file is the human-readable record of the reasoning. Dated usage reviews live in [`feedback/`](../feedback/).

## Auto-activation design

Once installed and enabled, the plugin's `SessionStart` hook (`hooks/hooks.json`) runs `hooks/inject-router.sh`, whose stdout is added to Claude's context. The injected `<orchestra-router>` block tells the session to classify **each** user request into one of two lanes before acting:

- **EXPRESS**: one self-contained change (or conversational/read-only), no decomposition, no design decisions, small expected context bloat. File count is explicitly *not* a criterion — incidental doc updates may ride along. Two gates keep the lane honest in both directions: the criterion is **expected context bloat, not the session's model tier** (being on an expensive model is not itself a reason to delegate), and **content the session already holds** — a spec it just designed, a fix it already worked out — is express regardless of size, since delegation cannot shrink context that is already held. Handled directly or via a single disposable cheap subagent, with no review pipeline (though the *verification run* is still handed to a cheap subagent so its output never floods the instructor). If scope or success criteria move mid-flight, express is aborted and the task re-routes to the orchestrated lane. (Lane criteria ported from `discus0434/customizable-agent-teams`.)
- **ORCHESTRATED**: everything else, and *whenever in doubt*. The session loads the `run` skill and follows the full cost-tiered pipeline.

The router block also lists explicit **tripwires** that force a mid-conversation re-route to ORCHESTRATED: hand-writing substantive code in 2+ files, a design discussion turning into an implementation request, or the session planning a multi-step implement-then-verify sequence for itself. Lane choices never persist across requests.

Three properties of the injection hooks:

- **Hybrid gating**: the hook first tries to read the top-level `model` field from the SessionStart input JSON (via `python3`; the field is officially omittable). When the model is identified as Opus/Fable (case-insensitive substring match), the router is injected without its self-gate paragraph; when it's identifiably a cheaper model (Sonnet/Haiku), nothing is injected at all — zero context cost. Only when the model can't be determined (missing field, bad JSON, no `python3`) does it fall back to injecting the full self-gated text, which tells the session itself to ignore the block unless its main model is Opus or Fable. The script never exits nonzero, so a parsing failure can't disrupt session startup.
- **Compaction-proof**: injected context is not automatically re-added after compaction, so the hook registers the `SessionStart` matchers `startup|resume|clear|compact` — the router survives new sessions, resumes, `/clear`, and context compaction.
- **Recency-proof**: a single SessionStart injection sits at the very top of the context and decays in long sessions — transcript analysis found instructor-model sessions doing 200+ direct edits with zero mention of the lane classification. The `UserPromptSubmit` hook (`hooks/remind-router.sh`) therefore re-surfaces a short reminder next to every new prompt. Since UserPromptSubmit input is not guaranteed to carry a `model` field, `inject-router.sh` persists its gate verdict (`instructor`/`cheap`/`unknown`) to `${TMPDIR:-/tmp}/orchestra-router-state-<session_id>`; the reminder hook reads that file, staying silent on cheap-model sessions and falling back to a self-gated reminder when the verdict is unknown.

## Gate discipline (v0.14.0)

Rounds are the pipeline's real cost, and most slow runs are slow because rounds were spent badly rather than because a model was weak. v0.14.0 replaces the blind 3-retry counter with four rules (`skills/run/SKILL.md` §11):

- **A rejection must cite the contract.** A reviewer may not invent a stricter requirement, tighten a tolerance the spec left open, or reject a design choice the spec delegated; `cited_contract` is a required field on every finding. Improvements it noticed but the contract doesn't require go to `optional_hardening`, which never blocks a pass. Gold-plating reviewers were the most expensive failure mode available — they burn every remaining round on work nobody asked for and still fail the task.
- **Findings carry a defect `family`, and the reviewer sweeps the family before reporting.** One round closes a whole class of bug (rounding-carry, input normalization, error-type mismatch, ordering, serialization round-trip, …) instead of one instance; a one-finding-per-round loop is how a 3-round budget gets spent on three siblings of the same defect.
- **Two gates, then a human-shaped decision.** One initial gate plus one incremental re-gate — the re-gate gets the previous verdict, the closed finding ids and the changed paths, and inspects only those plus plausible regressions (6 read-only shell invocations, first line `VERDICT: PASS|FAIL`). If it surfaces a family that predates the correction, the loop stops and returns `needsInstructor`: the *sweep* was wrong, so another automatic round would just find the next sibling.
- **Escalate the class; never resume the failed worker.** Workers report `ESCALATE` when the packet doesn't settle a needed decision, the change crosses their file ownership, or a failure isn't locally explainable — that bumps `light`→`standard`→`deep` without consuming a gate, since a mis-sized packet is not a defect. The same family failing twice bumps it too, and security/auth/concurrency work starts at the higher tier rather than proving itself through a cheap failure. Corrections always go to a *fresh* invocation via a self-contained packet: the rejected instance is anchored on the reasoning that produced the defect.

- **Probes are throwaway; kept tests must name the mistake they catch (v0.42.0).** The reviewer's floor is ≥3 *hypotheses* about likely implementation mistakes, not ≥3 permanent tests. Each probe is deleted unless it found a defect or guards a likely, silent mistake, and the verdict reports `tests_kept` plus `tests_loc_added`/`impl_loc_changed` so test inflation is visible before the diff lands. Contracts name the mistakes to detect instead of a case table to satisfy, and never ask for tests of constant values, untouched behavior, "this is unchanged", or wall-clock time (`skills/run/SKILL.md` §6 rule 8). Observed before the change: 1,050 test lines for 340 implementation lines in one 3-task run, 134 of them deletable with every suite green.

Workers are also capped at ~12 shell invocations (reviews 12, re-gates 6). An interrupted or budget-exhausted review is a FAIL, never a PASS.

## Worktree isolation (v0.16.0)

Seven weeks of transcripts contain **35 destructive VCS commands run by workers** against the user's shared working tree — `git checkout -- <paths>`, `git restore`, `git reset --hard`, `git clean -fd` — spread across haiku, sonnet, and opus workers alike. The countermeasure had been prose, escalated three generations deep in the worker prompts ("Never run git checkout…" → "The ONE exception…" → "THE WORKING TREE IS ALREADY DIRTY AND THAT IS EXPECTED AND CORRECT"), and the accidents continued after each escalation. A worker's only view of the world is `git status`; a diff it did not author reads as contamination whatever its prompt says.

So as of v0.16.0 the fix is structural. `agent-exec dispatch` isolates by default (`--isolate auto`) whenever the tree holds uncommitted work, giving the worker a tree that contains its own work and nothing else — the mistake becomes a no-op. This covers external CLI executors, which the Workflow tool's own `isolation: 'worktree'` option cannot reach even though that is where most implementation work runs.

`agent-exec isolate create` carries the user's uncommitted work into the worktree and commits it as a baseline (so `isolate diff` shows only the worker's changes), copies gitignored dependency directories by copy-on-write clone (~2s for 83MB/9.5k files, versus every worker re-running its own install), and reuses one worktree per `--task` across retry rounds. Where [git-worktree-runner](https://github.com/coderabbitai/git-worktree-runner) is installed it goes through `gtr`, so the user's own `gtr.copy.include` patterns and `gtr.hook.postCreate` steps apply — and orchestra never *writes* gtr config: what it needs is injected for one subprocess via `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n`, leaving `.git/config`, `~/.gitconfig`, and the committable repo-root `.gtrconfig` untouched.

A second layer, `hooks/guard-worker-vcs.sh` (`enforcement.worker_vcs`, on by default), denies destructive VCS commands from *subagents* against any non-`orchestra/*` branch. The main thread is never affected, and inside its own worktree a worker may reset freely. A third layer, `hooks/guard-worker-tree.sh` (`enforcement.worker_tree`, on by default), closes the same gap for plain writes: a worker that *has* an orchestra worktree but edits the user's main tree anyway. That is not hypothetical — a worker whose prompt opened with "WORKING TREE: `<path>` / cd there FIRST … Never touch files outside that path" ignored the line and ran Edit/Write against the same files in the user's tree, and its rejected output would have been what the user kept. Claude Code's own `sandbox.enabled` cannot cover this (session-global, and Bash-only). A fourth layer, `hooks/cleanup-worktrees.sh` (`enforcement.session_cleanup`, on by default), removes the finishing session's worktrees at `SessionEnd` — but only the ones with no uncollected changes, since a dirty worktree is the only record of what a worker tried. That hook is session-scoped by construction, so leftovers still accumulate — a killed session, a run from before the hook shipped, a legacy sessionless `orchestra/<task>` worktree, `session_cleanup: "off"`, or a tree that was dirty at `SessionEnd` and kept on purpose. `agent-exec isolate sweep` (v0.30.0) is the after-the-fact counterpart: repo-wide rather than session-scoped, running `git worktree prune` first, applying the *same* review gate as `isolate remove` so uncollected work is reported and kept, skipping the running session's own trees unless `--include-current`, filtering by branch-tip age with `--older-than`, and deleting `orchestra/*` branches that outlived their worktree only on an explicit `--branches`. `--dry-run` previews through that identical gate, so the preview and the sweep can never disagree. The `/cleanup` skill is its user-facing front end.

The same release moves the *primary* cleanup off `SessionEnd` entirely, because that hook is unreliable in both directions: it never fires for a session that is killed, crashes, or has its terminal closed, and when it does fire it is racing a teardown timeout that a slow removal loses. The `run` skill's Workflow template therefore sweeps at **run end** — the moment the last gate closes, every diff is collected, and nothing is racing it — via the same cheap haiku relay that emits telemetry; `orchestra-delegate` does the same before reporting on the no-Workflow path. `SessionEnd` and `/cleanup` become backstops rather than the mechanism. Two changes make that safe and fast: the removal gate now skips `git diff --binary` whenever the patch text cannot change its verdict (a worktree nobody collected costs one `--name-only` instead of a full binary diff, which is what made bulk cleanup outrun its timeout), and parallel sessions are protected by a heartbeat — every `agent-exec isolate`/`dispatch`/`route`/`run` call touches `alive/<session8>` beside the run ledger, and a sweep leaves alone any session seen within `--live-window` (default 120 min). A session with no heartbeat counts as dead, so worktrees predating the mechanism stay reclaimable.

## Programme scale, the shared stash, and worktree leases (v0.31.0)

The largest orchestration found in local history was not an orchestra run: an ultracode session drove a whole product overhaul through 13 hand-written workflow runs — 499 agents, 115.9M tokens, 32.5 hours, ~70 of ~220 packages integrated — before exhausting the user's weekly quota with six days left on it. Its shapes were sound and are now part of the playbook; its cost and its two accidents are what the rest of this release is for.

- **`skills/run/references/programme.md`** (and SKILL.md §13) adopts the shapes. *Planning workflows*: scoped auditors each pipelined into an adversarial verifier whose default verdict is `refuted`, a completeness critic that sees only the titles of what survived, and an Opus synthesizer that emits packages with `files_owned`/`depends_on`; design → critique → revise, or two opposing designs and a judge; reconcile → cross-check; and a reality check of every spec against the code immediately before scheduling, because `files_owned` is a prediction. *A dependency scheduler*: a package starts when its dependencies are integrated and nothing with overlapping files is in flight; a failed dependency blocks its dependents. *A rolling integration base*: one integration worktree per programme, every package's dispatch token minted with `--workdir` pointing at it, so each package starts from everything integrated so far and a serial Sonnet integrator replays it back with `agent-exec isolate integrate`, resolving conflicts and reverting only the package that broke. *Carry-over*: work a package cannot do because another package owns the files goes to a carry file and is triaged into the not-yet-started spec that owns them, never through the instructor's context. Each package still runs through the unchanged two-gate `runTask()`.
- **Budget first.** That run pinned a model on one script of 13; everything else inherited Opus, with up to three review rounds per package. The programme template chunks the work (`maxPackages` 12, `maxInFlight` 4 by default), returns the pending set for the next chunk, and routes every role through the class table.
- **The stash stack is shared.** `refs/stash` is one stack for every worktree of a repository; two parallel workers stashed four seconds apart and each popped the other's entry, swapping their changes between worktrees. `guard-worker-vcs.sh` allowed exactly that — stash inside a worker's own `orchestra/*` worktree, and `stash pop` anywhere. It now denies stash push/pop/apply/drop/clear to workers in every worktree, and points them at the new **`agent-exec shelf`** — the same job (`push [--keep-index] [-- PATH...]`, `pop`, `apply`, `drop`, `list`, untracked and binary files included) with entries stored as patches in the worktree's own git dir, so no other worktree can see or pop them. Workers had real uses for stash — the cueweave logs show it mostly for confirming a new test fails without the fix and checking a staged subset alone — so a denial without a replacement would just push them into ad-hoc file copies. jj was considered and rejected for this: it refuses to run inside a git linked worktree, and its own workspaces carry no `.git` for the rest of the tooling to use.
- **One writer per worktree.** A message sent to a running workflow engineer resumed a *copy* of it; the copy and the original committed into the same worktree two seconds apart. The new `guard-worktree-lease.sh` (`enforcement.worktree_lease`, on by default) leases each linked worktree to the first subagent that writes into it, denies a different subagent's writes while the holder is active, and releases the lease at `SubagentStop`. The playbook's "resume a subagent with `SendMessage`" advice now excludes agents a running Workflow spawned.


## Rollback, diffs, and competing implementations (v0.14.0)

Version control is effectively free, so the pipeline assumes it (`skills/run/references/isolation.md`). A baseline snapshot is taken before the first worker — `git init` if the tree isn't a repo — and between attempts, which buys two things: the reviewer diffs against something real instead of inferring the worker's footprint from prose, and a bad correction is rolled back rather than patched on top of.

Isolation also pays off beyond the safety case above: it lifts the constraint that parallel workers must own disjoint files, so genuinely tangled work can be parallelized, exploratory failures cost nothing, and **competing implementations of one contract** become practical: run N variants, judge them against one adversarial suite, and treat their disagreements as a defect report about the *spec* — ambiguity found before the bug ships. It costs N× implementation tokens, so it's for the risky core, not the default shape.

Workers never touch VCS state; snapshots, merges, and cleanup belong to the supervising layer. Descendant agent branches are unrestricted and disposable, but the branch that becomes the PR is built from the accepted diff and carries no checkpoints, rejected variants, or worker-only files. Non-interactive CLI executors also get their approvals front-loaded, since a permission prompt they can't surface becomes a silent stall.
