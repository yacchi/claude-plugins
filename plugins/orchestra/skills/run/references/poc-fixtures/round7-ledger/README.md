# round7-ledger: 根本原因 vs 症状(既存コードの読解と失敗の解釈)

Round 4・5は「バグ1つ・症状が原因を直接指す」構成だったため、全候補が満点で天井に張り付いた。本ラウンドは `standard` worker に必要な技能 — 既存コードベースを読み、原因から離れた場所に現れる失敗を解釈し、**失敗しているケースの未テストの兄弟まで正しくなるように根本原因を直す** — を、安価なモデル(Haiku 5.5、GPT-5.6 Luna 等)の間で弁別するためのフィクスチャである。

題材は Python 3.11+ 標準ライブラリのみで書いた小さな請求・台帳パッケージ `ledger`(16モジュール(`__init__`・`__main__` を除く)、約1,170行)である。層構成は parsing(CSV)→ domain(Money・暦・モデル)→ pricing/proration → tax/rounding → reporting/statements である。

## 構成

| パス | 内容 |
|---|---|
| `buggy/` | 候補に渡す起点一式。`ledger/`(バグ入り)・`tests/`(可視テスト68件)・`pytest.ini`・`SPEC.md`・`TASK.md` |
| `reference/` | 正解実装 `ledger/` と、`buggy/tests/` とバイト単位で同一の `tests/`・`pytest.ini` |
| `hidden/` | 採点用の非公開チェック43件(`test_hidden.py`)と、チェックごとに税率メモを初期化する `conftest.py`。候補には絶対に見せない |
| `symptom_patches/` | バグごとの「症状だけ直すパッチ」4本(`rounding`・`proration`・`parsing`・`cache`) |
| `verify.sh` | 採点スクリプト |

## 使い方

```bash
F=plugins/orchestra/skills/run/references/poc-fixtures/round7-ledger
mkdir -p /tmp/candidate-r7 && cp -R "$F/buggy/." /tmp/candidate-r7/
# candidate に /tmp/candidate-r7 で TASK.md を読ませて直させる
"$F/verify.sh" /tmp/candidate-r7
```

`verify.sh <candidate-dir>` は任意の cwd から実行でき、常に終了コード0で終わる。候補ディレクトリには一切書き込まない。採点対象は候補の `ledger/` パッケージだけであり、これを一時ディレクトリへコピーし、**元の** `buggy/tests/` と `pytest.ini` を添えて可視スイートを実行する(候補が `tests/` や `conftest.py` を書き換えても結果に影響しない)。出力は次の4点である。

1. 可視スイートの PASS/FAIL と失敗テスト名
2. 候補の `tests/` が元とバイト単位で同一か(`yes`/`NO`)
3. `N/43 hidden checks passed`
4. ファミリー別の通過数(`R`・`P`・`C`・`K`・`G`)と失敗したチェックID

症状パッチの適用は `patch -p1 -d <buggy のコピー> < symptom_patches/<bug>.patch` で行う。4本は別々のファイルに触れるので、任意の順で重ねて適用できる。

## 仕込んだバグ

4つのバグは互いに独立で、すべて別の層・別のファイルにある。`reference/` と `buggy/` の差分はこの4箇所だけである。

### 1. 共通の丸めヘルパー(ファミリー R) — `ledger/money.py`

- **原因**: `round_amount` が `amount.quantize(quantum)` と丸めモードを指定していない。`decimal` の既定コンテキストは `ROUND_HALF_EVEN`(銀行丸め)なので、仕様(§2.3 四捨五入・ゼロから遠い側へ)と端数ちょうど0.5のときだけ食い違う。
- **可視の失敗**: 呼び出し元の1つである税計算のテストだけに現れる(`test_tax.py::test_half_cent_rounds_up`、`::test_negative_half_cent_rounds_away_from_zero`)。値引き・数量計算・按分・為替換算・表示も同じヘルパーを使っているが、可視テストではちょうど0.5の値を避けてある。
- **誘惑的な症状パッチ**(`rounding.patch`): `tax.py` の中だけで `quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)` にする。可視テストは通るが、他の呼び出し元は銀行丸めのままで、さらに通貨の最小単位(JPY は0桁、KWD は3桁)を無視するようになる。
- **捕まえる hidden チェック**: R01〜R09(9件すべて)。加えて回帰チェック G04(JPY の税額が `123.40` になる)がパッチで新たに壊れる。

### 2. 暦・按分(ファミリー P) — `ledger/dates.py`

- **原因**: `days_in_month` が手書きの「拳の山」則 `30 + month % 2` と `year % 4 == 0` によるうるう年判定でできている。1〜7月は偶然正しいが、8〜12月の月の長さがすべて逆になり、2100年・1900年をうるう年と誤判定する。同じファイルにある正しい `is_leap_year` は使われていない。
- **可視の失敗**: 8月の日割り1件のみ(`test_proration.py::test_partial_august`)。可視テストは1〜6月と2024・2025年の2月だけを使う。
- **誘惑的な症状パッチ**(`proration.patch`): `if month == 8: return 31` と見えている月だけを特例にする。
- **捕まえる hidden チェック**: P01〜P07(9・10・11・12月、年またぎ、2100年2月、世紀年のうるう判定)。パッチ後に通るのは P08(8月丸ごと)だけである。8月以降の偶奇を反転させるだけの部分修正でも P02・P07(2100年)が残る。

### 3. CSV 金額パーサー(ファミリー C) — `ledger/parsing.py`

- **原因**: `parse_amount` が会計表記の括弧 `(150.00)` を剥がすだけで負号を付けない(`negative = True` が抜けている)。
- **可視の失敗**: パーサーのテストではなく、**集計層**のアサーションとして現れる(`test_reporting.py::test_revenue_by_month_nets_credit_notes`、`::test_customer_balances_net_of_credits`。月次売上・顧客残高の合計がずれる)。可視のパーサーテストは桁区切りと `-` 表記だけを検査している。
- **誘惑的な症状パッチ**(`parsing.patch`): レポート側で「`kind == "credit"` で正の金額なら符号を反転」する。仕様 §4 は「kind は記述用で金額の符号を変えない」と明記している。
- **捕まえる hidden チェック**: C01〜C08(8件すべて。パーサー直接、`read_entries`、括弧付き `adjustment` の売上・残高、税集計、請求書、整合性チェック)。さらに回帰チェック G10(正の金額の credit はそのまま正)がパッチで新たに壊れる。

### 4. 税率メモ化のキーが粗すぎる(ファミリー K) — `ledger/rates.py`

- **原因**: `rate_for` のモジュールレベルのキャッシュのキーが `(region, on.year)` になっている。SOUTH は 2025-07-01、EAST は 2026-04-01 に年の途中で改定されるため、同じ年の中で最初に引いた税率が以後も返る。
- **可視の失敗**: 他のテストとの組み合わせでのみ失敗する。`test_invoice.py::test_south_invoice` が SOUTH の2025年3月を先に引き、その後 `test_tax.py::test_south_rate_after_revision`(2025年9月、7.5%を期待)が6%を受け取って失敗する。`test_tax.py` 単体で実行すると全件通る。
- **誤誘導コメント**(仕様の項目5): キャッシュの横に「改定は年に1回までなので (region, year) で十分」というもっともらしい説明と、「請求処理の前に `clear_rate_cache()` を呼ぶべき」という TODO を置いた。いずれも誤った修正方針を示唆する。
- **誘惑的な症状パッチ**(`cache.patch`): TODO に従って `build_invoice` の先頭で `clear_rate_cache()` を呼ぶ。可視テストは通る(後続の `build_invoice` がキャッシュを捨てるため)。
- **捕まえる hidden チェック**: K01〜K06(6件すべて。`rate_for` を改定前後の順・逆順で引く、EAST の同年改定、改定をまたぐ請求書と税集計、無関係な先行参照の後の `tax_for`)。別案の症状パッチ「`tax_for` の先頭でキャッシュを消す」も検証済みで、K01〜K03 が残る。

## 設計上の注意

- hidden の `conftest.py` はチェックごとに `clear_rate_cache()` を呼ぶ(存在する場合)。これがないと K ファミリーのバグが他ファミリーのチェックを汚染し、ファミリー単位の採点が成り立たない。K のチェックは前後関係を1つのテスト本体の中で作っている。
- `Money` の等価判定は数値比較なので(`1.230 == 1.23`)、hidden は量子化の桁数ではなく丸めた**値**だけを見ている。
- 可視テストは68件で、パラメータ化を使わず1関数1件にしてある。失敗するのは6件(バグ1: 2件、バグ2: 1件、バグ3: 2件、バグ4: 1件)。
- 指示によりこのディレクトリ以外は変更していない。`poc-fixtures/README.md` の表と `../poc-findings.md` への追記は、実際に候補を走らせた後で行うこと。
