# orchestra 外部エグゼキュータ検証ログ

Codex CLI・Copilot CLI・Claude(Sonnet/Haiku)をorchestraの`worker`/`hard_worker`/`independent-verifier`ロールに使う際のモデル選定・effort設定の根拠となった、一連のPoC(概念実証)の全記録。`SKILL.md` §9のポリシー(モデル・effort・料金表)は要点のみを載せているため、「なぜその設定になったか」を知りたいときはこのファイルを参照する。

日付はすべて2026-07-16前後の検証時点のもの。モデルのカタログ・料金・挙動は今後変わりうるため、重要な意思決定の前には再確認すること。

## 0. 検証方針

一貫して守った原則:

- **自己申告を信用しない。** 各候補(Codex/Copilot/Claude)の「完了しました」という報告は一切信用せず、必ず独立したテストハーネス(ビルド/型チェック/HTTPリクエスト/pytest等)で外側から検証した。
- **フィクスチャは正解実装で事前検証する。** テストケース自体が間違っていては意味がないため、各ラウンドで先に正解実装(reference implementation)を書き、テストハーネスがそれに対して全通過することを確認してから候補に投げた。バグを仕込むラウンドでは、バグ入り実装に対してテストが実際に失敗することも確認した。
- **コストは実測する。** Codex CLIは`codex exec --json`の`turn.completed.usage`から`input_tokens`/`cached_input_tokens`/`output_tokens`が取れるため、公式単価表と掛け合わせて実コストを計算した。Copilot CLIは`outputTokens`しか取れないため、コストは「出力トークン分のみの下限値」として明記した。Claudeの`Agent`ツールは`subagent_tokens`という合算値しか返さないため、入力想定/出力想定の両極から幅(bound)として示した。

## 1. orchestra自体の初回PoC(Haiku worker + Sonnet verifier)

3タスクを並列実行、エージェント計8体、4分23秒、サブエージェント合計246kトークン。

| 指標 | 値 |
|---|---|
| Haiku worker(4体)の出力トークン合計 | 9,638 |
| Sonnet verifier(4体)の出力トークン合計 | 19,135 |
| instructor(司令塔)がこの間に消費したトークン | 0 |
| instructorが受け取ったもの | 構造化JSON 約2KB |
| workerが自作した11個のテストが見逃したバグ | `formatBytes(1048575)` → `"1024 KiB"`(正しくは`"1 MiB"`。繰り上がり境界のバグ) |
| 修正までの往復回数 | 1回(adversarial verifierが検出し、workerが正確なフィードバックを受けて修正) |

verifierはworkerの約2倍の出力トークンを消費するが、workerの自作テストが完全に見逃したバグを検出できた。

最後の2行(`gpt-5.4-mini`、`gemini-3.5-flash`)はテストには通ったが、ユーザーの明示的な指示により方針から除外: 汎用・小型の「アシスタント」系モデルは、ベンチマーク速度に関わらず実開発用途には不向きと判断されたため。KimiとautoがCopilotの軽量候補として代わりに採用された。

**わかったこと:**
- 7構成すべてが、上記PoCでHaiku workerの自作テストを突破した境界値トラップを突破した — このタスクでは軽量モデルが弱点にはならなかった。
- この単純なタスクでは*精度*の差別化ができなかった(天井効果: 全通過)。差が出たのは*速度*のみ。SKILL.md §9.1のCoding Index(63/70/78)はサードパーティのベンチマークであり、このPoCとは別の証拠として扱うべき。
- 同じモデル(`gpt-5.6-luna`)でも、CopilotのハーネスはCodexより一貫して速かった(14.3s vs 41.5s、Codexは明示的に`effort: high`)。effortのデフォルト差やツール呼び出しのスキャフォールディングの違いで説明できる可能性があり、「一方のハーネスが原理的に速い」という主張ではない。
- Copilotの`auto`モードは、このコーディング風プロンプトに対して`gpt-5.3-codex`にルーティングした — 実開発タスクらしいプロンプトになるとcodex系モデルに寄る、という一般的な印象と一致(ルーティングはプロンプト依存なので、安定した挙動と決めつけず定期的に再確認すべき)。
- `kimi-k2.7-code`は正しい出力を出したが、同じ些細なタスクに対して内部のreasoning/イベント量が明らかに多かった(2ターン、JSONLで約800KB、他は概ね100KB未満)。ターン数や冗長さがwall time(壁時計時間)に影響するタスクでは注意。
- `MAI-Code-1-Flash`(Haiku代替候補として提案された)は、この時点のCopilot CLI 1.0.70のカタログには存在せず、`--model MAI-Code-1-Flash`の直接プローブで「利用不可」と確認された(→ 後述の通り、実際のIDは`mai-code-1-flash-picker`だったことが後で判明)。
- Copilotのセッション継続(`--resume=<sessionId>`。sessionIdは`--output-format json`の最終`result`イベントから取得)は実際に動作を確認した: 再開したセッションは前ターンの指示を正しく想起した。

## 3. Round 2: evalExprタスク + 公式単価による実コスト計算

Round 1のタスクは簡単すぎて精度を差別化できなかったため、より難しいタスクにした: `evaluate(expr)` — 右結合の`^`、単項マイナスと`^`の優先順位(`-2^2`は`-4`であり`4`ではない)、ゼロ除算・不正入力に対する厳密なエラーメッセージ契約を持つ、手書きの四則演算評価器(計22テストケース)。Codexの各実行は`codex exec --json`の`turn.completed.usage`の実トークン数を、[GitHubの公式単価表](https://docs.github.com/en/copilot/reference/copilot-billing/models-and-pricing)に掛けて実コストを算出した。

| Executor | Model / effort | 時間 | コスト | 正誤 |
|---|---|---|---|---|
| Codex CLI | gpt-5.6-luna / high | 69.8s | $0.033 | 22/22 |
| Codex CLI | gpt-5.6-terra / high | 49.8s | $0.060 | 22/22 |
| Codex CLI | gpt-5.6-sol / low | 51.7s | $0.127 | 22/22 |
| Codex CLI | gpt-5.6-sol / xhigh | 139.4s | $0.204 | 22/22 |
| Copilot CLI | gpt-5.6-luna | 22.9s | ~$0.011(出力分のみ、下記注意点参照) | 22/22 |
| Copilot CLI | auto(gpt-5.3-codexを選択) | 50.3s | ~$0.040(出力分のみ) | 22/22 |
| Copilot CLI | kimi-k2.7-code | 60.9s | ~$0.021(出力分のみ) | 22/22 |

**わかったこと:**
- **依然として天井効果。** Round 1より明確に難しいタスク(演算子優先順位・結合則のトラップ、厳密なエラー文字列)でも7構成全てが22/22で通過。Codex/Copilotの軽量〜上位ティア間で*精度*の差は出ず、差が出たのはコストと速度のみ。SKILL.md §9.1のサードパーティCoding Indexが唯一の精度シグナルであり、この2ラウンドのPoCは「失敗しなかった」という弱い証拠にとどまる。
- **Terra/highがSol/lowよりコスト・速度で優位だった**($0.060/49.8s vs $0.127/51.7s)。これはSKILL.md §9.1のサードパーティベンチマークから引き継いだ「Terraは(Lunaに)支配される」という一括りの扱いと矛盾する。ベンチマークのCoding Indexの序列自体を覆すものではない(天井効果では精度の主張を反証できない)が、`independent-verifier`の選択肢としてTerraを除外する前に、精度を差別化できるタスクで再検証する価値はある。
- **上記のCopilotのコストは下限値にすぎない。** `--output-format json`は`outputTokens`(アシスタントメッセージごとの出力トークン数)しか公開しておらず、入力トークン数は一切わからない。Codexの同等実行を見ると、この程度の小さなタスクでも入力トークンは無視できないコスト要素であり(1回あたり45k〜61kトークン、大半はキャッシュ済み=システムプロンプト/ツールスキーマのオーバーヘッドであってタスク本文ではない)、モデルによって総コストの40〜55%程度を占めていた。Copilotにも同程度の(見えない)入力オーバーヘッドがあるはずなので、Copilotのコスト欄は「本当の合計より低め」と読むこと。
- **Copilotの全実行で`"premiumRequests": 1`が一律計上されていた** — モデルによらず一定。標準的なサブスクリプションでは、生のトークン単価ではなく、フラットあるいは倍率ベースのプレミアムリクエスト枠で課金されている可能性を示唆する。GitHubの料金ページは現行の課金世代について倍率表を公開していない。上の単価表は方向性としての序列と捉え、実際のコストは各自のCopilot利用状況ダッシュボードで確認すること。
- **クライアント更新後にMAI-Code-1-Flashを再確認**(`copilot update prerelease`で1.0.70→1.0.71-3に更新)したが、`--model MAI-Code-1-Flash`は依然として`Error: ... is not available`。カタログにも変化なし。GitHubの料金ページでは**GA(一般提供)**として実価格(このテーブル中で最安のLightweightモデル、Lunaより安い)が掲載されていたため、クライアントが古いという話ではなく、アカウント/組織/プランレベルのロールアウト待ちの可能性が高いと判断した(この後 §8 で実際のIDが`mai-code-1-flash-picker`であることが判明する)。

Round 1〜3はすべて仕様書からのゼロベース実装であり、これは実際の`worker`ロールがリトライループで最も頻繁に行う作業(既存コードを読み、根本原因を見つけ、他を壊さずに直す)とは異なるスキルだった。Round 4はこれをテスト: トークンバケット式レートリミッタの3ファイル(`bucket.js`/`limiter.js`/`index.js`)に1つのバグ(refillの計算がミリ秒未満の経過時間を`Math.floor`で切り捨てるため、1秒未満のバーストでは全くrefillされない)を仕込み、症状の説明のみを渡した(失敗するテストファイルは渡さない。テストを繰り返し実行してgreenになるまで力技で収束するのを防ぐため)。検証は、注入可能な偽の時計を持つ独立の参照実装(3シナリオ、うち1つはバグ入り版でのみ失敗する)。

## 6. Round 5: 誤診断トラップ + Claude Sonnet/Haikuの追加

Round 4は、正直な症状説明さえあればどの生存組もバグを見つけられることを示した。Round 5は質的に異なるものを検証: 「安価・非力なモデルは誤った理解のまま突き進んでしまうのではないか」というユーザーの仮説に正面から挑む。キャッシュ層(`cache.js`/`normalizeKey.js`/`index.js`)に実バグ(`normalizeKey`が安全なトラッキングパラメータだけでなく*全ての*クエリパラメータを剥ぎ取ってしまうため、`?page=1`と`?page=2`が衝突して互いのコンテンツを返してしまう)を仕込み、各候補に渡すバグ報告には、もっともらしいが誤った診断(直近のTTL変更が原因だと決めつけ、`DEFAULT_TTL_MS`を下げるよう要求)を書いておいた。提案された修正をそのまま適用するだけのモデルは、TTLを下げ、`normalizeKey`はそのままにして失敗するはず。テストハーネスは**時計を完全に凍結**しており(テスト中に時間が一切進まない)、TTLは構造的に結果と無関係になるよう設計した — つまり、本当の根本原因を見つけない限り合格できない。

依頼により追加: **Claude SonnetとHaiku**を、Copilotのラッパー経由ではなく`Agent`ツールで直接同じタスクにディスパッチし、Codex/Copilotの軽量ティアと比較した。Claudeのコスト表は[Anthropicの公式単価](https://platform.claude.com/docs/en/docs/about-claude/pricing)を使用(Sonnet 5: 2026-08-31までの導入価格で入力$2/出力$10 per MTok、Haiku 4.5: 入力$1/出力$5 per MTok)。`Agent`ツールは入出力の内訳のない合算値`subagent_tokens`しか返さないため、Claudeのコストは点推定ではなく幅(全て入力/全て出力の両極)として示した。

| Executor | Model / effort | 時間 | コスト | 正誤 |
|---|---|---|---|---|
| Codex CLI | gpt-5.6-luna / high | 83.0s | $0.042 | 3/3 |
| Codex CLI | gpt-5.6-sol / xhigh | 77.4s | $0.194 | 3/3 |
| Copilot CLI | gpt-5.6-luna | 31.0s | ~$0.015(出力分のみ) | 3/3 |
| Copilot CLI | kimi-k2.7-code | 34.3s | ~$0.008(出力分のみ) | 3/3 |
| Claude Agent | sonnet | 44.4s | $0.076〜$0.380(合算37,972トークン、幅) | 3/3 |
| Claude Agent | haiku | 36.3s | $0.025〜$0.123(合算24,548トークン、幅) | 3/3 |

**トラップは誰も引っかからなかった — Haikuも含めて。** 6構成すべてが誤ったTTL診断を無視(あるいは明示的に否定)し、`normalizeKey.js`の過剰なクエリ剥ぎ取りという本当のバグを修正した。誰も`DEFAULT_TTL_MS`には触らなかった。Codexのsol/xhighは最終報告で明示的にこう述べていた:「5分のTTLは衝突を長引かせただけで、原因ではない」。Claude Haikuの要約も、促されていないのに全く同じ区別に言及していた。事前の仮説からすると意外な結果 — テストした最安ティア(Haiku、Luna)でさえ、もっともらしいが誤った診断として意図的に設計されたバグ報告には引っかからなかった。

## 7. Round 6: Go/Python/TypeScriptの実践規模フルスタックアプリ — 天井が崩れる

Round 1〜5はすべて1ファイル〜数ファイル・単一言語の範囲にとどまっていた。Round 6は実際の`worker`ロールの作業規模にはるかに近いものを検証: 1本の指示書から小さなタスク管理Webアプリを構築させる。**Go**(インメモリREST API — 作成/ソート付き一覧/更新、完全な入力バリデーション)、**Python**(注入可能な「今日の日付」を使うタスク統計 + 信頼できない「AI API」からの不正・範囲外な`confidence`を拒否しなければならないモックAIレスポンスのパーサー)、**TypeScript**(厳密に型付けされた`fetch`ベースのAPIクライアント + 純粋な表示変換ヘルパー)にまたがる、約8〜10ファイル・3つのツールチェイン・1本の共有仕様書。検証は言語ごとに完全に独立・自動化: `go build`/`go vet` + 実際に起動したサーバーサブプロセスに対する本物のHTTPクライアント(15項目)、候補のモジュールを直接importする`pytest`(11項目)、`tsc --strict --noEmit` + モックした`fetch`によるコンパイル後のユニットテスト(12項目) — 計38項目、すべて自己申告なし。ユーザーの要望により追加: Python/Go/TypeScriptはユーザーが日常的に使う言語であり、これがJavaScript以外を検証する初めてのラウンドだった。

| Executor | Model / effort | 時間 | コスト | スコア |
|---|---|---|---|---|
| Codex CLI | gpt-5.6-luna / high | 369.5s | $0.179 | 33/38(87%) |
| Codex CLI | gpt-5.6-sol / xhigh | 374.2s | $0.945 | 38/38(100%) |
| Copilot CLI | gpt-5.6-luna | 65.4s | ~$0.037(出力分のみ) | 38/38(100%) |
| Copilot CLI | kimi-k2.7-code | 193.4s | ~$0.047(出力分のみ) | 38/38(100%) |
| Claude Agent | sonnet | 222.0s | $0.117〜$0.586(幅) | 38/38(100%) |
| Claude Agent | haiku | 133.3s | $0.037〜$0.187(幅) | 36/38(95%) |

**ついに実際の、しかも別々の実バグが2社の最安ティアから出た:**

- **Claude Haiku**は優先度と緊急度のランク付け自体は正しかった(`high`/`medium`/`low` → ランク`0`/`1`/`2`)が、`order=desc`の向き反転を比較関数全体に適用してしまい、「タイブレークは常に`dueDate`昇順であるべき(ソート方向によらない)」というルールも含めて反転させてしまった。そのため`order=desc`ではタイブレークされたペアが降順`dueDate`で出てきてしまう。狭い範囲の、比較関数の合成ミス(向き反転の適用範囲を広げすぎた)であり、ランク付けの理解自体の誤りではない。
- **Codex `gpt-5.6-luna`/high**は独立した2つのミスを犯した: (1) 優先度ソートのasc/desc対応を完全に反転させていた — 優先度ランクが数値で`high=0, medium=1, low=2`とエンコードされているため(数値が小さいほど緊急)、「ランク数値の昇順」でソートすると実際にはhigh優先で並んでしまい、`order=asc`(緊急度が低い順)が意味すべきものの*正反対*になっていた。(2) `/tasks`という完全一致パスのルートしか登録しておらず、`/tasks/{id}`というパターンのルートを一切追加していなかったため、**PATCHリクエストは全て404になる** — 更新エンドポイントが全く機能しない。この2つ目のバグは検証スクリプター自体のJSONパースをクラッシュさせた(プレーンテキストの404ページは有効なJSONではないため)。これはまさに「自己申告を信用しない」という原則が捉えるべきシナリオ: ハッピーパスだけを自己テストする候補では、これを見つけられなかっただろう。

**未解決の重要な異変: 全く同一の`gpt-5.6-luna`モデルをCopilot経由でディスパッチした場合はすべて正解だったが、Codex自身のディスパッチでは正解しなかった。** これはモデルの重み以上に、周辺のハーネス/足場(2つのCLI間でのシステムプロンプトやツール呼び出しの慣習、自己検証の振る舞いの違い)が影響している可能性もあれば、単に単一試行における通常のサンプリングのばらつき(このPoCシリーズ全体を通じて各条件n=1)である可能性もある。このラウンド単体ではこの2つの説明を区別できない — 区別するには同一設定の複数回の反復実行が必要で、ここでは行っていない。「Codex Lunaは失敗し、Copilot Lunaは成功した」は、この1回の実行における実際の観察として扱うべきで、Copilotのハーネスが原理的に優れているという証明ではない。

**実務的な結論:** 単一関数・単一ファイル規模では、このPoCシリーズ全体を通じて5ラウンド連続で精度の差別化ができなかった。実際の複数ファイル・複数言語にまたがる機能規模 — 典型的な`worker`タスクの規模に初めて近づいたラウンド — では、2つの異なるプロバイダの最安ティアがそれぞれ1つずつ、本物の狭い範囲のバグを出した一方、それぞれの中位/上位ティアと、もう一方のプロバイダの最安ティアはクリーンだった。これはorchestraの中核設計を裏付ける具体的なデータ点: どのモデル・プロバイダが実装したかによらず、些細な変更を超える作業ではadversarial verifierを絶対に省略しないこと — タスクが「単一関数」から「小さな実機能」へと踏み越えた時点で、コストティアは正答率の信頼できる予測因子ではなくなる。

## 8. Round 6 追試: Codex Lunaのeffort変更 と MAI-Code-1-Flashの実IDの解明

Round 6の全く同じWebアプリのタスク/仕様書で、直接比較可能な形で2つの追試を行った。

**Round 6のCodex Lunaのバグは、モデル選択だけでなくeffortレベルが原因だった可能性がある。** Codexの`gpt-5.6-luna`はこのPoCシリーズを通じて一貫して`effort: high`で実行していた(SKILL.md §9.1のサードパーティベンチマーク自体のティア選択に合わせていた)。一方Copilotの`gpt-5.6-luna`はCopilot自身のデフォルト(CLIの出力からは直接確認できないが、ユーザー報告のUI挙動から見て`medium`相当と思われる)で動いていた。Codexの`gpt-5.6-luna`を`effort: high`ではなく`effort: medium`にしてRound 6を再実行した結果:

| Executor | Model / effort | 時間 | コスト | スコア |
|---|---|---|---|---|
| Codex CLI | gpt-5.6-luna / **high**(Round 6時) | 369.5s | $0.179 | 33/38 |
| Codex CLI | gpt-5.6-luna / **medium**(この追試) | 316.3s | $0.131 | **38/38** |

effortパラメータを変えただけで、失敗する実行が全問正解に変わり、しかも安く速くなった。これも各方向でn=1の比較にすぎないため、「effortを上げると考えすぎて悪化する」という一般法則を証明するものではないが、その仮説を支持する具体的な実データであり、推論モデルにおいて「熟考すればするほど良くなるわけではない」という既知の現象とも整合する。**この結果を根拠に、このプラグインのCodex `gpt-5.6-luna`のデフォルトの`worker`ポリシーを`effort: high`から`effort: medium`に変更した**(`examples/orchestra.json`)。Copilotのluna側のポリシーも、Copilot自身のデフォルトがどのラウンドでも良好に機能していたことから、一貫性のため揃えて`medium`にした。

**もう1つの解決事項: MAI-Code-1-Flashの実際のCLIモデルIDは`mai-code-1-flash-picker`であり**、`MAI-Code-1-Flash`(料金ページや対話的UIのピッカーに表示される名前)ではなかった。ユーザーが対話的UIで利用可能であることを確認し、`copilot -p "hi" --model mai-code-1-flash-picker --allow-all-tools -s`でCLIからも動作することを確認した。Round 6と同じWebアプリタスクで実行:

| Executor | Model | 時間 | コスト | スコア |
|---|---|---|---|---|
| Copilot CLI | `mai-code-1-flash-picker` | 115.0s | ~$0.049(出力分のみ) | 36/38 |

MAIは今や実際に使える、有望な候補になった — そこそこ速く、安く、Python/TypeScript部分と、Goバックエンドの大部分を正しく処理した。しかし**Codex `gpt-5.6-luna`/highと全く同じ優先度ソートのasc/desc反転ミス**を犯した(どちらも「昇順の緊急度」を「優先度ランク数値の昇順」と取り違えて逆になっていた)。2つの独立したモデルが同一の反転ミスを犯したことは、この特定のトラップ(`high=0`という数値エンコーディングが、意味的なソート方向と逆になる)が、1社のハーネス固有の癖ではなく、高速・安価系モデル全般にありがちな失敗パターンである可能性を示唆する。MAIは「使える確定候補」にはなったが、たった1回の(それも完璧ではない)実行結果だけで「一番良い」と結論づけるのはまだ早い。

## 9. 再現性検証: Copilot Lunaは本当に安定しているか(n=5)

Copilot `gpt-5.6-luna`はRound 6で最速・最安・満点という抜きん出た結果を出しており、ユーザーがSonnetの代わりに日常使いする候補として検討するに値するかという疑問が生じた。このPoCシリーズの他の全ての比較は各条件n=1だったため、これを同一タスク・新規ディレクトリで4回追加実行した(合計n=5)。

| 実行 | 時間 | 出力トークン | コスト(出力分のみ) | スコア |
|---|---|---|---|---|
| 元(Round 6) | 65.4s | 6,243 | $0.037 | 38/38 |
| 追試2 | 65.3s | 7,203 | $0.043 | 38/38 |
| 追試3 | 63.9s | 7,311 | $0.044 | **37/38** |
| 追試4 | 74.5s | 9,994 | $0.060 | 38/38 |
| 追試5 | 57.7s | 6,543 | $0.039 | 38/38 |

**5回中4回は満点。5回目に1件、別種の不具合が出た** — Round 6の優先度ソートのバグの再発ではなく、`client.ts`における実際の`tsc --strict`のコンパイルエラー(`Argument of type 'unknown' is not assignable to parameter of type 'string | undefined'`。エラーレスポンスのボディを解析するヘルパー内で、catchした例外かパース済みJSON値を型ガードなしに使っていたと思われる)。

このタイプの不具合は、ロジックバグ(優先度ソートの反転や、PATCHルートの登録漏れなど)と比べて実害の重みが軽い点に留意したい。ロジックバグは特定の入力でしか症状が出ず、自作テストをすり抜けることさえある一方、`tsc --strict`のような型チェックエラーはコンパイラ/CIが**即座に、決定的に**検出し、エラー箇所もピンポイントで示してくれる。見つけるコストがほぼゼロで、直すのも通常は1〜2行の修正で済む。したがって「5回に1回、何らかの不具合が出た」という数字を、優先度ソートのバグと同じ重みで受け取るべきではない — 発見コストと修正コストがまるで違う。

全5回を通した集計: **190項目中189項目通過(99.5%)**。時間(57.7〜74.5秒)・コスト($0.037〜$0.060)ともに外れ値なくタイトにまとまっていた。

**結論: 再現性は高いが完璧ではない — ただし唯一の不具合は「安価な部類」のもの。** この速度とコストは実運用のデフォルトとして検討するに値する水準であり、観測された不具合の重み(5回に1回、しかもすぐ気づいて安く直せる型エラー)は、Round 6で他の安価ティア全般に見られた傾向と同程度かそれ以下である。Sonnet規模の日常使いとして採用するのは、生の出力をそのまま信用するのではなく、検証(テスト・CIでの型チェック・`orchestra-verifier`パスなど)と組み合わせる前提であれば妥当な判断といえる — これはCopilot Luna固有の注意点ではなく、このPoCシリーズ全体が一貫して積み上げてきた結論そのものである。

## 10. 総括: モデル選定についての現時点の結論

6ラウンド・6種類のタスク形状・3プロバイダ、さらにRound 6の追試2件と再現性検証1件を通しての結論:

- 単一ファイル〜小規模複数ファイルの規模では、5ラウンド連続で精度の差別化ができなかった。誤った理解のまま突き進むことを狙って設計したトラップ(Round 5)でさえ、最安ティアを含め誰も引っかからなかった。
- 実際の複数ファイル・複数言語の機能規模(Round 6)になって初めて、2つの異なるプロバイダの最安ティアからそれぞれ実バグが出た。
- その後の追試で、少なくとも一方の失敗(Codex Luna)は`effort`パラメータを`high`から`medium`に変えるだけで解消し、新たに確認できたMAI候補は独立に酷似した失敗モードを再現した。
- Copilot Lunaに絞った再現性検証(n=5)では、非常に強いが完璧ではないという結果になった(190項目中189通過。唯一の不具合はロジックバグより軽微な型エラー)。

**総合結論: コストティアは速度の予測因子としては一貫して機能したが、単純な孤立タスクでの正答率の予測因子としては一度も機能しなかった。しかしタスクの規模・複雑さが実機能の領域を超えた瞬間、このシリーズでテストした安価ティア(Codex Luna、Claude Haiku、MAI、そして十分な試行回数で見たCopilot Luna自身)は、いずれもどこかで実際の不具合を見せた。** これは、どのモデル・プロバイダ・effortレベルで実装されたかによらず、adversarial verifierの段階を任意ではなく必須のステージとして扱うという、orchestra自体の設計を裏付ける具体的な根拠である。
